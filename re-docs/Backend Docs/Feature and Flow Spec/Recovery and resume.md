# Recovery and resume
> Type: Flow · Status: aligned · Updated: 2026-09-12

## Intent
Processes crash mid-run — deploys, OOMs, worker stalls — and the work already done must not be lost or silently redone. This flow exists so a crashed run is detected, parked with its progress intact, and resumed by an explicit operator decision that picks up where the run stopped instead of re-executing completed tool calls.

## Architectural decision
The shape is three linked choices. First, orphan handling is a two-hop `→ orphaned → resumable` walk, never a direct jump to `failed` or back to `queued` `[Observed]` — the intermediate state preserves the checkpoint and forces an explicit resume decision instead of auto-retry or silent drop `[Inferred]`. Second, progress is a checkpoint watermark plus a `completedCallIds` set, merged atomically in-DB (monotonic `greatest()` watermark, `jsonb_agg(distinct)` union) so parallel batch writers can't clobber each other `[Observed]` — and resume means skipping those call ids with a `[resumed]` marker, not replaying them `[Observed]`. Third, resume crosses domain boundaries as data, not execution: `resumeRun` only flips `resumable → queued` and hands back `{ run, checkpoint }`, leaving delivery to Queue and re-execution to Runtime `[Observed]`. The rejected alternatives are visible in what the code refuses to do: no auto-retry on sweep, no direct sweep-to-`queued` (would re-run blind), no sweep-to-`failed` (would destroy resumability), and no checkpoint read-modify-write in callers (would lose ids under concurrency) `[Inferred]`.

## How it works
While a run executes, Runtime keeps it alive with a 15s `touchRunHeartbeat`, because long LLM calls and approval waits would otherwise look dead. Separately, the orphan sweep fires on an interval and selects rows whose `updatedAt` is older than `ORPHAN_AFTER_MS` in the candidate live states — Runs owns this reaper, and it deliberately excludes `waiting_for_approval`, which belongs to the Approvals TTL path. Each stale row is walked `→ orphaned → resumable` with a `run.status_changed` emit per hop, and rows stranded mid-walk by an earlier crash (`orphaned`, or `cancelling` from an interrupted cancel) are self-healed on the next pass. A `resumable` run then waits for an operator: `POST /api/runs/:id/resume` (or the `run:resume` socket) calls `runsGate.resumeRun`, which accepts only `resumable`, flips it to `queued`, and returns the stored checkpoint. The transport layer — Routes/Sockets, not Runs — converts that checkpoint into a `resumeContext` and delivers it: in bullmq mode by re-enqueueing on the `runs` queue with the real `runId` plus the resume payload, in inline mode by calling `runtimeGate.execute` directly. Queue's run worker picks the job up, resolves the agent, and hands `(runId, resumeContext)` to the executor; the executor walks the row to `running` (`queued → starting → running`, or the full chain if handed a still-`resumable` row) and stamps the context onto the execution packet. The agentic loop then skips every tool call whose id is in `completedCallIds`, marks it `[resumed]` in call order, executes only the rest, and keeps touching the checkpoint per call — so a second crash resumes from a superset of the same ids. When the loop finishes, the normal close walk (`completing → verifying → completed`, or `failed`/`cancelled`) retires the run.

## Current state
Real in both modes: the sweep (two-hop + self-heal + per-hop emits), `resumeRun` with its `resumable`-only guard, the atomic checkpoint merge, the agentic skip, and the 15s heartbeat all run today. In inline mode the sweeper starts on API boot and resume executes in-process; in bullmq mode the API suppresses local timers and the worker owns the `orphan-resume` repeatable, with resume going through the `runs` queue (3 attempts, 15min lock, progress heartbeats). Nothing in this flow is stub or flag-gated — the adjacent flags (`RESEARCH_V1`, `SWARM_V1`, `APPROVALS_ENABLED`) change what executes, not how recovery works. Known rough edges that are real but unenforced: the resume payload rides outside the typed `EnqueueRunInput` (`resumeContext`/`resumeFrom` via `@ts-ignore`, worker prefers `resumeContext`), and inline resume plus bullmq enqueue failures are fire-and-forget/log-only, so the resumer can't tell delivery failed.

## Open gaps
- `historyRef` (large-history offload for deep resume) is threaded through checkpoint/resume types but no loader was observed — full-history resume fidelity is unverified.
- Resume skip is verified for the agentic loop only; what resume means for conversational, coding (pi-core session vs heartbeat/sweep interplay untraced), research, and swarm (which wipes + recreates `swarm_tasks` per run) is unverified.
- `checkpointSeq` mirror column's consumer (ordering vs display vs resume cutoff) was not found — possible legacy duplicate.
- Resume payload typing and precedence (`resumeContext` over `resumeFrom`) are enforced by nothing; a producer/consumer rename would fail silently at runtime.
- Second resume is single-use by construction (`queued` rejects a repeat `resumeRun`), and delivery failures are invisible to the resumer — operator retry/visibility UX is unaddressed.
