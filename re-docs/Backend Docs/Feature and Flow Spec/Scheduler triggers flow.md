# Scheduler triggers flow
> Type: Flow · Status: aligned · Updated: 2026-10-20

## Intent
An agent (or operator) can ask for work to happen later — once after a delay or repeatedly on a cron — without holding a run open. This flow exists so a schedule booking becomes a durable BullMQ job (or an honest inline timer when Redis is absent) that fires by persisting a real `system-scheduler` message and emitting it; when the schedule names a target agent, the fire then starts that agent's run.

## Architectural decision
Persist-before-emit with an ephemeral fallback: the fire handler writes the `system-scheduler` message via `messageGate.append` (sequence + insert + `message:new`) first, degrading to an unpersisted (sequenceNumber 0) emit when the DB is down — so a scheduled fire is honest either way `[Observed]` (`scheduler-worker.ts:42-90`, `message-service.ts:387-406`). Booking and firing are split across domains: Tools owns the schedule-creation UX (cron parsing, BullMQ booking, inline fallback), Queue owns the durable trigger (scheduler queue + worker + emits), Messages owns the row `[Observed]`. 2026-10-20 (A1): booking now also persists the schedule itself to the local store BEFORE it is armed, so an armed timer that dies with the process is still a known row; the Queue domain computes the next fire time from the schedule intent, and a schedule that cannot be persisted is not armed at all `[Observed]` (`scheduler-local-store.ts`, `tool-registry.ts`). 2026-10-20 (A2): inline timers now belong to the Queue domain (`scheduler-rearm.ts`), and boot re-arms every persisted row against the wall clock — an overdue one-shot fires once as catch-up, cron arms the next boundary and skips missed ticks, and a row the local tier cannot track is skipped and reported. The timer itself still cannot outlive the process, so the documented loss window is "fire due while the process was down"; it is no longer silent `[Observed]` (`scheduler-rearm.ts`, `create-app.ts`). 2026-10-20 (A3): the inline fire now has an explicit run contract. A row with `targetAgentId` starts that agent's run after the message is persisted — one run per fire, shared busy registry with the socket trigger, channel pin honored, paused/offline/missing targets skip with a system notice. A row without a target still ends at fan-out, and the BullMQ worker path is unchanged (see gaps) `[Observed]` (`scheduler-dispatch.ts`, `scheduler-rearm.ts`).

## How it works
1. The `system_scheduler` tool (absent when `SYSTEM_SCHEDULER_ENABLED=false`) takes a channel task plus either a cron expression or a `delayMs`: the cron path books a repeatable BullMQ job via `upsertJobScheduler` (`scheduled:cron`), the one-shot path adds a delayed job (`scheduled:trigger`) — both carrying channel/task/message/workspace (`tool-registry.ts:554-591`).
1a. 2026-10-20 (A1): before either path, the tool validates the cron shape / delay and persists the schedule through `queueGate.saveSchedule` — the row lands in `<workspaceFolder>/vfs/.crowdos/scheduler/scheduled_tasks.json` with `nextRun` computed by the Queue domain. A failed persist aborts the call and arms nothing (`tool-registry.ts`, `scheduler-local-store.ts`).
1b. 2026-10-20 (A2): inline mode additionally rejects a cron form it cannot track (`*/N * * * *`, N 1-60) before the row is written, so no persisted row is left that boot re-arm could never fire (`tool-registry.ts`). 2026-10-22: a second trackable form was added - `M */H * * *` (minute M, every H hours, H 1-24) - because the 2-4h watchdog cadence cannot be expressed in the minute field (`*/120` would silently behave like an hourly one). The local tier computes the next boundary for both forms; anything else is still rejected.
2. In inline mode the same call hands the persisted row to `queueGate.armSchedule`: the Queue domain computes the fire time, writes it back to `nextRun`, and owns one `setTimeout` per row (`scheduler-rearm.ts`). On boot, `queueGate.rearmSchedules()` does the same for every active row — overdue one-shots fire once (catch-up then deactivate), future one-shots arm the remainder, and cron arms the next boundary strictly after `now` without replaying missed ticks (`create-app.ts`, `scheduler-rearm.ts`).
3. In bullmq mode the scheduler worker (started via `startSchedulerWorker`, idempotent singleton) routes every `scheduled*` name — plus `kind`/task-shape fallbacks — to `handleScheduledTrigger` (`scheduler-worker.ts:91-104`).
4. The handler persists a `system-scheduler` message via `messageGate.append` (sequence + insert + `message:new`) (`scheduler-worker.ts:43-71`); when the DB is unreachable it emits an ephemeral `message:new` (sequenceNumber 0, unpersisted id) instead (`scheduler-worker.ts:72-90`).
5. It then emits `scheduled:triggered` for observability (`scheduler-worker.ts:93`); the inline fire emits the same event alongside its message, with the schedule row id as the payload id (`scheduler-rearm.ts`).
6. Inline, `dispatchScheduledRun` runs between the message and the `scheduled:triggered` emit (`scheduler-dispatch.ts`). 2026-10-22: it no longer starts a run of its own - it posts the wake as a message and hands it to the shared dispatch (see 6a/6b), which resolves the target, applies the busy check and executes the run. The wake always requests the Agentic runtime; the channel's pinned runtime stays a preference.
6a. 2026-10-22: a wake is now an automated MESSAGE, not a private side channel, and it carries the SCHEDULER's own words. The schedule row records `authorAgentId` - the agent that booked it - and the fire delivers that agent's `message` (or its `task` description) under the agent's own sender id and name, so an agent that schedules its future self receives its own words back. A row with no author (the operator-created watchdog) is delivered as a system message. `dispatchScheduledRun` posts the wake through the shared dispatch (`shared/core/message-dispatch.ts`) - the same owner an operator's message goes through - so the target is resolved by the standard ladder: an explicit `targetAgentId` (expressed as a mention, exactly like a typed `@Name`) or else the channel's PINNED agent. The wake always routes the AGENTIC runtime (`explicitRuntime`), whatever the channel's runtime pin says; the pin stays a preference. The message is persisted once (by the shared dispatch, which owns the row), the busy registry, the paused/offline notices and the tenant-scoped execution are the shared ones, and a wake therefore cannot pick a different agent than a typed message would.
6b. 2026-10-22: the wake dispatch itself is the shared one (`shared/core/message-dispatch.ts`): the target ladder (mention, else the channel's pinned agent, else the channel default, else the category owner, else the L0 roster), the busy key, the paused/offline notices and the tenant-scoped execution are the same code an operator's message runs through. An explicit `targetAgentId` is expressed as a mention, so it takes the same path as a typed `@Name`.
7. The BullMQ worker path is not wired to the dispatcher yet: a BullMQ-booked row with `targetAgentId` persists and emits as before but does not start a run (see gaps).

## Current state
Real in both modes: BullMQ delayed + repeatable (cron) bookings, transactional persist-then-emit firing, ephemeral fallback on DB outage, `scheduled:triggered` observability emit, inline `setTimeout` timers, `SYSTEM_SCHEDULER_ENABLED` kill-switch (default on). 2026-10-20 (A1): every schedule is persisted to the workspace local store before it is armed, with the next fire time computed by the Queue domain — a schedule that cannot be persisted is not armed. 2026-10-20 (A2): inline timers are Queue-owned and re-armed on boot against the wall clock, so a restart recalibrates instead of losing or replaying schedules; overdue one-shots fire once as catch-up, missed cron ticks are skipped. Bullmq-only: durable jobs that survive restarts. 2026-10-20 (A3): an inline fire with `targetAgentId` starts exactly one run for that agent after the message is persisted, with busy/paused/offline/missing handling and the channel pin honored; a row without a target still ends at fan-out. The BullMQ path still ends at fan-out. 2026-10-22: the inline wake is an automated message through the shared dispatch - the channel's pinned agent answers it (or the explicitly targeted one), it always runs on the Agentic runtime, and the inline cron form gained `M */H * * *` for the 2-4h watchdog cadence.

## User Decision:

## Target Contract
> Status: Target. Flow-scoped view. Authority stays in linked domain specs.
* Scheduler fire has an explicit run contract: whether it starts a run, as which agent, via which enqueue path. Trails ending at fan-out are forbidden. 2026-10-20 (A3): satisfied inline (`targetAgentId` → `dispatchScheduledRun` → one run); the BullMQ path remains an open trail.
* Inline schedules are durable or explicitly ephemeral with a documented loss window. Silent restart loss is forbidden.
* Inline cron either supports full cron or rejects non-conforming expressions. Silent 60s fallback is forbidden.
* Scheduler-queue failures have gate-visible listing. Log-only scheduler failures are forbidden. Stop and remove helpers are gate ports or explicitly drain-only. Authority: Queue, Tools standards.
## Open gaps
- Inline timers are still process-memory only; A2 removes the silent loss by re-arming on boot, but a fire due while the process was down is only caught up for one-shots — cron deliberately skips missed ticks.
- Inline cron understands only `*/N * * * *` and now rejects anything else at booking (no row is written), so misconfiguration fails loudly instead of becoming a silent 60s interval (A2, closes the earlier gap). 2026-10-22: a second trackable form was added, `M */H * * *` (minute M, every H hours, H 1-24), for the 2-4h watchdog cadence; every other form is still rejected at booking.
- Scheduler-queue job failures are log-only with no gate-visible listing (`getFailedJobs` covers only the `runs` queue).
- Stop/remove-scheduler helpers exist but are not gate ports — only `drain` can stop scheduler workers publicly.
