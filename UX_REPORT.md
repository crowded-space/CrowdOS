# 1 Method and baseline: what production grade means and where CrowdOS stands

## 1.1 What the user asked for, restated as a research contract

// @exec fairly: user wants heavy reasoning, verbose, complete steps, no summarization. The deliverable is UX_REPORT.md. The object of study is desktop app UI UX for AI infrastructure. The references are VSCode, Discord, Slack, ChatGPT Desktop, Claude Desktop, CodeBuddy, Steam. The required reasoning chain per finding is: what the pattern is, why it is that way, and why CrowdOS should apply or adapt it. The final synthesis must say what the target CrowdOS desktop experience should look like.

I interpret production grade as meeting all six tests at once. First, the app survives real enterprise conditions: cold start, slow disk, flaky network, locked screen, offline database, permission denial, thousand-channel workspaces, ten-thousand-message histories, long streaming runs, and hostile pasted content. Second, the app is legible to a new operator in minutes and efficient for an expert in months, without two different apps. Third, every destructive or costly action is reversible, previewable, or explicitly confirmed, and every autonomous action is attributable and interruptible. Fourth, the app respects the host OS: windowing, tray, shortcuts, file dialogs, notifications, accessibility APIs, updater, and security sandbox behave like a native citizen. Fifth, the app is measurable: performance budgets, error budgets, audit trails, cost attribution, and usability metrics exist and are visible where decisions happen. Sixth, the app stays coherent as it grows: one navigation model, one command surface, one settings model, one design token system, one empty versus loading versus error language.

Enterprise grade adds four more tests. Multi-identity and multi-workspace operation must be safe: leaving a workspace, switching a channel, changing a mount, or changing a model must never leak context across boundaries. Governance must be in the flow, not beside it: approvals, policy, redaction, retention, and export controls appear at the moment of action with enough context to decide. Cost and risk must be legible before commit: tokens, dollars, runtime choice, tool scope, and file write scope are shown before the run, during the run, and after the run. Supportability must be designed in: diagnostics, logs, degraded-mode banners, retry paths, and honest fallbacks replace silent failures and fake data.

AI infrastructure adds three specific burdens that normal chat or normal IDE work does not carry. The system acts over time, not just answers once, so the UI must show work in progress, partial results, tool calls, diffs, cancellations, retries, and resumption. The system spends money and touches files, so the UI must make scope visible and stoppable. The system has multiple minds in one room, so the UI must show who said what, who did what, which runtime did it, which context it saw, and what it cost, without turning the transcript into an ops dashboard.

## 2.1 VSCode: the benchmark for dense, keyboard-first, extension-governed desktop work

### 2.1.1 What VSCode shows, step by step

VSCode opens to a shell that never moves: Activity Bar on the far left as a narrow icon rail, Side Bar next to it as the working panel, Editor Groups in the center as tabbed surfaces, Panel below as terminal plus problems plus output plus debug console, Status Bar along the bottom as a dense telemetry strip. The Command Palette under Ctrl Shift P or Ctrl K is the universal verb surface. The Explorer tree is a tight 22 px row list with disclosure chevrons, muted file icons, flat full-width selection, inline dirty and error badges, and popover hovers that reveal full paths. Search, Source Control, Run and Debug, Extensions each reuse the same Side Bar slot rather than inventing new windows. Tabs carry dirty dots, close affordances, split left right, drag to reorder, and preview versus pinned distinction: single-click previews in italic, double-click pins. The bottom Panel is a tabbed drawer with maximize, its height user-resizable and remembered. Settings are JSON plus UI in split view, scoped as User versus Workspace versus Folder, with search that filters on modified only. The Status Bar shows branch, sync state, errors and warnings counts, language mode, indentation, encoding, line endings, feedback bell, and remote or codespace target, each segment clickable to its action. Notifications stack bottom-right as toasts with Manage versus Do not show again, never modal unless destructive. The integrated terminal is first-class, multiple shells, split, kill, maximize, persistent across window reload. Extension hosts run out of process so a crashing extension does not take the window; untrusted workspaces gate extension auto-run under Workspace Trust. Update ships via staged auto-update with release notes, never blocking the editor. Offline works fully for editing, with extensions and sync degrading with explicit badges.

[Observed in CrowdOS for contrast] Your FileExplorer.tsx already copies the VSCode row metrics deliberately: ROW_HEIGHT 22 plus INDENT 12 plus CHEVRON_GUTTER 16, muted extension icons, flat full-width selection via rowClasses, roving focus tree with role tree and treeitem and aria-level and posinset and setsize. That is the right borrowing and the comment says why: the tree must read as a file list rather than a stack of cards. Your tree also adds lazy fetch per directory, cached children, spinner on expand, Refresh and filesystemRevision re-read, amber NoticePanel for failure, and a separate read-only Zone A root for L0. Good. What you do not yet copy is the rest of the VSCode contract: preview versus pinned tabs, dirty plus error badges on rows, tabbed editor groups with splits, bottom drawer with remembered height, JSON plus UI settings with scope, status bar as clickable telemetry, and extension-grade isolation for agent tooling.

### 2.1.2 Why VSCode is shaped that way, reasoned fully

First, stability of spatial memory. The Activity Bar never reorders itself based on content. The user builds muscle memory that Source Control is always third, Search always second. This matters because professional tools are used 8 hours a day for years: every pixel move costs thousands of re-aims. VSCode therefore fixes the shell and lets content change inside slots, never the slots themselves. CrowdOS should reason the same: your App.tsx shell with left nav plus center chat plus right roster is already slot-stable, but your right panel violates it by swapping entire meanings under one flag. Section 4 returns to this.

Second, keyboard as primary, mouse as accelerator. The palette exists because menus do not scale to thousands of commands contributed by extensions. Typing a fuzzy verb is faster than hunting nested menus, and it is self-documenting: it shows the keybinding next to each result so the user graduates from palette to shortcut. The why is discoverability without clutter. CrowdOS has OmniSearchModal under Ctrl K but it currently searches channels plus messages plus agents plus tools as navigation, not verbs. The reasoning gap is that CrowdOS actions like switch runtime, pin mode, clear channel, mount folder, open diff, approve run, cancel run, retry provider are not palette verbs yet, so experts must click. That is why palette must become command-first, not search-only.

Third, preview versus pinned tabs as attention economy. Single-click opens a preview that reuses one slot, double-click or edit pins. The why is tab-strip overflow: without preview, every peek leaves a tab and the strip becomes an unreadable 40-tab graveyard. With preview, exploration is cheap and commitment is explicit. CrowdOS SandboxCodeViewer opens one selectedSandboxFile docked in chat. Without preview semantics, opening five files to compare means five competing states or last-wins confusion. The reasoning transfers directly: file open should distinguish peek versus keep, and diff review should distinguish browse versus apply.

Fourth, Status Bar as ambient awareness without interruption. Errors plus warnings counts, branch dirty, language mode are always visible but never modal. Clicking jumps to the cause. The why is that professionals need continuous partial attention: they glance 100 times a day and act 3 times. Toasts would be 100 interruptions. A status strip is zero interruptions plus 3 fast jumps. CrowdOS telemetry today lives in RightSidebar footer behind Channel versus Global tabs and requires opening the roster. Cost, tokens, active agents, channel count are therefore invisible during the act of spending. That placement inverts the VSCode lesson: the most decision-relevant numbers must be ambient during composition, not buried in a drawer.

Fifth, Workspace Trust and extension isolation as enterprise risk design. VSCode could have let any folder auto-run any extension. It chose to gate with Trust because opening a repo is the most common attack vector. Out-of-process hosts mean one bad extension cannot freeze typing. The why is blast radius: the editor is the last app the user will forgive for losing keystrokes. CrowdOS runs agents that read files, write files, call tools, spend money, and call networks. That is strictly more dangerous than extensions. Therefore CrowdOS needs a stronger Trust equivalent: per-mount scope badges, per-run tool scope preview, per-file apply gates, and degraded-mode honesty when the sandbox or DB is unavailable. Your explorer-model.ts mountWarning and amber notices are the seed of this, but they are not yet a Trust gate in the composer path.

Sixth, settings as layered JSON plus UI with scope. User versus Workspace versus Folder with modified-only filter exists because enterprise users inherit base config from org, override per repo, and need to audit what is non-default. JSON preserves diffability in git; UI preserves approachability. CrowdOS mounts already have a three-level inheritance chain Workspace then Category then Channel override with replace semantics. But the UI does not show the chain as a chain. FileExplorer header shows effective source badge with tooltip, which is good, yet there is no single Mounts view that shows Workspace value, Category value, Channel value side by side with which wins highlighted. VSCode teaches that inheritance without a side-by-side inspector breeds mystique and misattribution. CrowdOS will hit the same support tickets: why is this channel seeing that folder. The inspector is the fix.

Seventh, bottom Panel as user-sized drawer. Terminal plus Problems plus Output share one resizable drawer with tabs and maximize because developers constantly trade vertical space between code and logs. Remembered height respects that trade as a preference, not a default. CrowdOS Sandbox panel already measures live DOM to compute full versus dock heights and tweens explicit px heights with one driver. That engineering is excellent and VSCode-like in spirit. The gap is memory and multiplicity: your sandboxView min versus dock versus full resets to dock on every new file, does not remember per-channel height, and holds one file at a time. VSCode would remember per workspace and allow splits. Long agentic runs that emit code plus logs plus diffs need that multiplicity: code peek, terminal tail, diff list visible without swapping.

### 2.1.3 What CrowdOS should steal, adapt, reject from VSCode

Steal verbatim: 22 px tree rows with muted icons and full-width selection, already done, keep locked. Steal ARIA tree contract with roving tabindex, already done, keep. Steal skeleton versus empty versus error tri-state per panel, already partly done via NoticePanel, extend to every panel. Steal Ctrl K as universal entry, but expand OmniSearchModal from navigation search to command palette with verbs. Steal status strip thinking: add a thin composer-adjacent strip showing runtime, pinned agent, mount short path, tokens this channel, cost this run, degraded flags, each clickable.

Adapt, do not copy: Activity Bar as icon rail does not fit CrowdOS because your left rail is workspaces plus channels, not tools. Instead adapt the principle as a stable slot map: far-left workspace switcher 56 px, channel nav 240 to 280 px, center chat fluid, right ops 260 to 320 px, bottom drawer for code and diffs and logs. Adapt tab groups as conversation plus file multi-surface: keep chat as the primary scroll, but allow pinned file tabs above the sandbox drawer so peeking three files does not lose place. Adapt settings scope UI: reuse VSCode User versus Workspace versus Folder pattern as Workspace versus Category versus Channel for mounts, defaults, runtimes, and safety, with modified-only filter and effective-value highlight.

Reject: VSCode extension marketplace model of arbitrary third-party code with broad API is not your model. CrowdOS tools are agent-executed with approvals and audit, not renderer-injected UI. Do not import the extension API attack surface. Also reject VSCode minimap and breadcrumbs density for chat: chat is temporal, not spatial, and needs date dividers plus unread dividers plus jump-to-present, not code minimaps.

## 2.2.2 Why Discord is shaped that way, reasoned fully

First, servers as isolation with low switching cost. Discord could have been one global feed. It chose hard server boundaries with per-server identity, roles, channels, and notification settings because communities need both belonging and exit: you can be loud in one server and muted in another. The rail keeps switching to one click plus unread summarization so isolation does not become amnesia. CrowdOS Workspaces are the same: isolated agents plus channels plus config plus history per Workspace, same name in two Workspaces means different instances. The why transfers exactly: AI work also needs loud versus quiet contexts, experimental versus production mounts, cheap versus expensive model scopes, without cross-leak. Your hash routing plus workspace switch plus unread badges already honor this. The remaining lesson is per-workspace notification and per-channel mute must be first-class and persistent, which you partly do via crowdos_muted_channels in localStorage but do not yet surface as a unified notification center.

Second, categories as permission and attention grouping, not folders. Discord categories group channels for collapse and inherited permissions, not for file paths. The why is cognitive chunking: 60 channels become 6 chunks of 10, each collapsible, each with its own add affordance. CrowdOS Categories do the same for channels plus inherited defaults plus mounts. Your toggleCategoryCollapse plus chevron plus aria-expanded plus per-category create button gets the interaction right. What Discord adds that you lack is category-level mute, category-level description, and category drag reorder, all of which matter once a Workspace grows past 20 channels. Without bulk mute, a noisy category forces per-channel clicks; without reorder, growth becomes archaeology.

Third, presence as ambient trust. Green versus yellow versus red versus gray dots, streaming or voice states, custom status, typing indicators every few seconds. The why is coordination without polling: you glance and know who is around, who is busy, who is typing, so you time your message. CrowdOS AgentRow presence plus StatusBadge thinking versus executing versus pulsing variants plus isSwarmActive is the agent analogue, but agents are not humans: thinking can last 40 minutes and cost dollars. Discord presence is binary and free; agent presence must be durational and costly. That is why CrowdOS must show not just executing but executing for 12 minutes plus 48k tokens plus 0.14 dollars with Stop affordance at the presence site, not just in the chat header. Your per-bubble STOP plus header Stop is close, but roster rows themselves are not yet stoppable or cost-aware.

Fourth, mentions and unread as triage, not just decoration. Discord distinguishes unread white pill versus mention red badge versus muted gray, and Inbox collects only mentions plus replies plus thread updates. The why is volume: in a 10k-member server you cannot read everything, so the app must answer what needs me. CrowdOS multi-agent channels have the same volume problem from the other side: five agents can emit 200 tool lines while you look away. Your ChannelButton unread plus mention dot plus Jump to present pill with missed count plus viewport-anchored paging is the right triage skeleton. What is missing is an Inbox equivalent: a Mentions plus Approvals plus Failures view that collects across channels where you or L0 were named, where approval awaits, where a run failed or was cancelled. Without it, an approval in channel 14 waits silently while you read channel 3.

Fifth, composer constraints as social contract. Discord shows slowmode countdown, max length, upload limits, permission denials inline at the composer with plain copy. The why is preventing wasted effort: you learn before you type that you cannot speak here. CrowdOS composer already blocks empty sends, caps 4000 chars with truncation warning, caps 5 MB and 10 files, disables mount-less actions with tooltips. That matches Discord. The gap is cost and scope preflight: Discord tells you slowmode before send; CrowdOS should tell you this send will run Coding runtime with Crow plus write scope to this folder plus estimated context size before send, not after spend. That is the AI-infrastructure upgrade to Discord composer discipline.

Sixth, settings as server-scoped modal with left nav. Discord server settings are a full overlay with Overview plus Roles plus Emoji plus Stickers plus Moderation plus Audit Log, each with Save versus Reset bar. The why is blast radius clarity: every toggle says which server it affects, unsaved changes are explicit, audit log shows who changed what. CrowdOS WorkspaceSettingsModal with tabs plus overview plus channels plus agents plus models is structurally right. The lesson is to add three Discord details: an explicit unsaved-changes bar so mount plus default plus safety edits do not silently apply or silently lose, a per-scope effective-value preview so Category versus Channel overrides are legible, and an audit surface for approvals plus mount changes plus model changes, because enterprise admins will ask who allowed writes to prod.

Active rail plus unread 99 plus plus mention dot, already done, keep locked. Ctrl K quick switcher, already present, extend to commands. Degraded strip with single recovery action, already done via OfflineBanner plus Database Offline card, keep pattern and extend to provider outage plus ledger offline plus filesystem jail denial.
