# P4 Settings, Threads and Authority

> Type: Spec — Status: draft — Updated: 2026-10-21

## Purpose

This spec covers the fourth priority band of the Discord-derived work: the settings surface, the authority layer around it, the run-thread surface, and the desktop shell. It is the band where CrowdOS is furthest from a coherent model — the Permissions & Roles tab is cosmetic by its own admission, `Agent.roleId` is set but never persisted, three permission vocabularies coexist, the stored permission blobs enforce nothing, there is no channel-membership model, the agent avatar is a level-derived emoji with no control, and the run-thread drawer is marked `[pending]` even though most of it is already built.

Every item here is **additive**. Nothing is removed, renamed or re-skinned. Where a Discord pattern collides with a locked CrowdOS rule, the Discord pattern is re-shaped and the conflict is written down in `## Risks and blockers` rather than applied silently.

The headline feature is **RE-P4-01, the agent profile picture**: an image uploaded once into the local CrowdOS workspace directory and reusable by any agent in that workspace. The research corpus already fixed the storage design (`../CrowdOS Understanding/Storage and Media Model.md:110-117`), so this spec does not re-derive it — it executes it, and it also presents the cheaper house-pattern alternative honestly, because the two options are not equivalent in what they deliver.

## How to read this spec

Each item is a self-contained, executable unit with a fixed nine-row shape. Read the rows in this order:

| Row | What it tells you |
|---|---|
| `Area` | The files the item touches. If a file is not listed, the item does not touch it. |
| `CrowdOS current` | What exists today, cited as `file:line`. If the item assumes a behaviour that the code does not have, this row is where the error shows. |
| `Discord reference` | The Discord Findings doc and the specific mechanism borrowed. A Discord mechanism with no CrowdOS counterpart is recorded in `../Traceability Matrix.md` under `## Gaps`, not here. |
| `Target (additive)` | What changes **and what is preserved**. The preserved half is normative: it is the do-not-break list for that item. |
| `Steps` | Numbered, executable. Names the files, functions, store slices, socket events, migrations and routes. |
| `Acceptance criteria` | Objectively checkable statements. Every one is verifiable without a screenshot. |
| `Test` | The test file and what it asserts, through which public surface (`AGENTS.md` §2: through the domain gate, or the socket/REST API for transport code). |
| `Depends on` | Other item IDs in this band, or `NONE`. |
| `Invariants` | Which `AGENTS.md` §5 invariants the item touches, and how each still holds afterwards. |

**The item count is 11, not 10.** The task brief grouped "per-channel role/authority grouping" and "the Desktop shell delta follow-ups" into one item. They are split here into **RE-P4-10** (client roster, `packages/client`) and **RE-P4-11** (Electron shell, `packages/desktop`) because `AGENTS.md` §3 says one feature is one domain, and a single item spanning the client and the shell would have no single owning gate, no single test surface and no single review boundary.

**Break-reading rules.** An item that names a new socket event, a new shared type, a new DB migration, a new REST route or a new dependency is a **breaking-change surface** under `AGENTS.md` §5. Each such surface is named in the item and its approval question is routed to `## Risks and blockers` and to `../Open Decisions.md`. None of them may land without that approval.

**Testing surface constraint (read this before writing a test).** The client vitest environment is `node` (`packages/client/vitest.config.ts:6`) and the client declares no `jsdom` and no `@testing-library/react` (`packages/client/package.json:15-41`), so component *rendering* is not unit-testable today. Every client item in this band therefore extracts a **pure logic module** — tested in the `node` vitest environment — and adds a Playwright spec under `e2e/` where a real DOM assertion is the only honest way to check the behaviour. A DOM test environment would be a **new dependency** and needs sign-off: it is `../Open Decisions.md` #15 and it is **not** approved. The desktop package has no test runner at all (`packages/desktop/package.json:14`); RE-P4-11 names its own prerequisite in its `Steps` and in `## Risks and blockers` R13.

**ID space.** `RE-P4-01` … `RE-P4-11`. The full scheme (`RE-P0-nn` … `RE-P4-nn`) is stated in `../_index.md`.

## Scope

**In scope**

- The Admin Console settings surface (`packages/client/components/workspace/modals/WorkspaceSettingsModal.tsx`), its 13 tabs, and its role/permission model.
- The role model: persistence, scope, vocabulary, and the broken `Agent.roleId` link.
- The stored-but-unenforced permission blobs on `agents`, and the decision of what to do with them.
- Channel membership as a data model, because it is the precondition for a channel-scoped roster.
- Per-agent authority display in the client projection.
- The run-thread surface and its graduation to the canonical run-branch view.
- Per-channel role/authority grouping inside the existing tier-grouped roster.
- The `packages/desktop` shell follow-ups drawn from the Discord shell delta.
- The agent profile picture (RE-P4-01), including the content-addressed media store and the binary-serving route.

**Out of scope**

- The message list, the composer, the scroll model, the shortcut registry and the ARIA surface — those are P0, P1, P2 and P3. This spec references them only where P4 touches them (RE-P4-09 touches the transcript's run cards; RE-P4-08 touches the settings modal's search).
- The Router's tier mapping, the escalation chain, L3 statelessness and every other runtime rule — `AGENTS.md` §5.2, §5.3 and §5.4 are load-bearing and are **not** touched by any item here. RE-P4-05 is the only item that touches an enforcement path, and it does so only by *proposing* enforcement points for a user decision.
- Any product feature that is Planned/Pending in `CrowdOS.md` §34. Where one would be needed, it is routed to `../Open Decisions.md` rather than built (see RE-P4-06 and Open Decisions #7).
- The `re-docs/` corpus. `AGENTS.md` §6 requires the owning Domain Spec to be updated **in the same task** as the code change; this spec names which doc that is, but does not edit it.

**Non-goals of this spec**

- No item replaces a CrowdOS surface. The Admin Console stays a modal. The roster stays tier-grouped. The run thread stays a drawer. The shell keeps its own security policy.
- No item introduces a role as an authority input. `AGENTS.md` §5.3 is absolute: authority comes from the level, never from a name, a label, a colour or a badge.
- No item enables enforcement of the `permissions` blob. RE-P4-05 is a decision item, and the choice is the user's.

## Dependencies and build order

The dependency graph inside this band is small and it is strictly acyclic. There is one hub: **RE-P4-03** (the `roleId` round-trip), which RE-P4-07 needs before a role can be shown, and RE-P4-07 in turn feeds RE-P4-10. RE-P4-06 feeds RE-P4-10 as well.

```
RE-P4-01  (avatar)        ── independent, new column + 2 routes
RE-P4-02  (roles)         ── independent, new table + 5 routes
RE-P4-03  (roleId)        ── independent, new column + client plumbing
RE-P4-04  (vocabulary)    ── independent, client-only
RE-P4-05  (enforcement)   ── independent, DECISION ONLY — nothing lands until answered
RE-P4-06  (membership)    ── independent, option A is read-only
RE-P4-07  (authority UI)  ── depends on RE-P4-03
RE-P4-08  (settings UX)   ── depends on RE-P4-04
RE-P4-09  (thread)        ── independent, new read route
RE-P4-10  (roster groups) ── depends on RE-P4-06, RE-P4-07
RE-P4-11  (desktop shell) ── independent
```

**The band-level ordering** (the full wave plan, including the P0–P3 items this band interacts with, is in `../Build Sequence.md`):

1. **Three surfaces in this band are shared with the parallel bands, and the lower item id owns the behaviour.** RE-P4-06 and RE-P4-10 extend the roster's channel-scoped participant section, which **RE-P1-02** owns; RE-P4-09 extends the run-thread drawer, which **RE-P1-05** (the focus contract) and **RE-P2-05** (the message-anchored thread model) touch. This band extends; it does not re-implement. The shared surfaces land in different waves, so they are never in flight at once.

2. **RE-P4-05's decision lands first, but its implementation lands last.** The decision is cheap and blocks nothing else; the enforcement work touches the Router and the tool executor, which is the highest-blast-radius change in the band and must not land before the measurement harness (P3-01) exists to check it.
3. **RE-P4-03 → RE-P4-07 → RE-P4-10** is the one chain with no slack. It is also the chain that turns a cosmetic role into a visible one, so it is the first authority work to ship.
4. **RE-P4-02 lands immediately before RE-P4-03**, in two consecutive waves, because both add a migration and both add a server leg; splitting them across unrelated work would put two half-finished persistence stories in the tree, and collapsing them into one wave would make one wave carry two migrations and two sets of consumers.
5. **RE-P4-01 is self-contained** and lands right after the measurement harness, because it introduces the first binary leg in the product and therefore needs its own performance and size checks.
6. **RE-P4-08 lands after RE-P4-04**, because a settings surface that stages edits must stage a truthful edit set.
7. **RE-P4-11 is independent** and can land at any time; it is scheduled last only because it is the lowest user-visible urgency.

**The one hard ordering constraint across the whole corpus:** the UX_GUIDELINE drift items are corrected **before** any wave in this band lands, in the same task as the docs that describe them. A wave that implements against a guideline that still describes a `rightSidebarOpen` boolean, four right-panel views and a 56 px rail would be implementing against a document that is known to be wrong.

## User Decision:

## Target Contract

> Status: Target. CrowdOS is canon. Every item in this band is additive; the Discord patterns are reference material, not a design source. Where a Discord pattern collides with a locked CrowdOS rule, the CrowdOS rule wins and the conflict is recorded in `## Risks and blockers` rather than applied.

* **Authority comes from the agent tier, always.** `agents.authority_level` is the only authority input in this band. A role id, a role name, a role colour, a badge, a group header or a permission switch may **never** grant, imply, gate or hint at a capability (`AGENTS.md` §5.3; `UX_GUIDELINE.md:21`; `CrowdOS.md:1502-1519`).
* **A role is always displayed beside the tier.** Every surface that shows a role shows the agent's `L{n}` chip with it, and the tier renders first in DOM order. An agent with no role renders exactly as it renders today.
* **Roles are per-workspace and non-authoritative.** Where persisted, they are scoped by `workspaceId`, they are display labels, and the Domain Spec says so. A role id that is settable but not readable is a defect, not a placeholder.
* **One permission vocabulary for role labels.** The two vocabularies that coexist today are reconciled into one registry with one id per permission. Unknown ids are preserved and shown, never silently dropped. The agent runtime permission blob is a **different list**, named as such wherever both are visible.
* **The stored permission blob is either enforced or labelled advisory — never both and never neither.** The Agents Domain Spec states which, in the same task as the code. Enforcement, if chosen, may only **narrow**: it may never raise authority, never widen a channel set, and never bypass a tier rule.
* **`agents.avatar` keeps its meaning.** The level-derived emoji is never overloaded with a path, never reinterpreted, and never rewritten by an upload or a tier change. A new agent picture lives in a new nullable `agents.avatar_path`; the emoji is the fallback and the tier seed.
* **An uploaded picture is workspace-local and content-addressed.** The blob lives inside the owning workspace folder under `vfs/agents/media/`, is shared by every agent in that workspace that references it, and is never readable from another workspace. The read path fails closed on any path that escapes the owning folder (`AGENTS.md` §5.10, §5.11).
* **Local-first holds for every new surface.** The file write is the commit; the database row is a best-effort replica. The agent picture, the role list and the role assignment all work with no `DATABASE_URL` configured (`AGENTS.md` §5.12).
* **Gate discipline holds for every new server surface.** The agent routes call `agentGate`; the role routes call `roleGate`; the channel-membership routes call the Channels gate; the run-branch route calls the Runs gate. Nothing imports past a gate (`AGENTS.md` §3; `packages/server/scripts/check-gates.mjs`).
* **The Admin Console stays a modal.** The 13 tabs keep their ids, their order and their labels; the `tabs` array stays the single registry and the header title still derives from it. The unsaved-changes bar, the effective-value preview and the settings search are **additions inside the existing surface**. A routed settings page is not built here (`../Open Decisions.md` #10).
* **A value that cannot be resolved renders empty, never plausible.** The effective-value preview shows only what a resolver would actually honour. An unknown permission renders "Unknown permission". A participant set derived from authorship is labelled "Participants seen in this channel", never "Members".
* **The run branch is the canonical run surface.** The drawer stays the only thread model, the parent prompt stays pinned, intermediate tool lines never post back, and only the final answer can post — and it posts with a link back to the run.
* **The desktop shell keeps its own security policy.** `packages/desktop/security-policy.ts` is CrowdOS's baseline: `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`, the loopback-only CSP. The zod IPC allowlist stays an allowlist, `window.crowdos` stays the only renderer-visible bridge, the OS window frame stays, and the tray stays the single menu surface. Discord's disabled `EnableEmbeddedAsarIntegrityValidation` fuse is the posture CrowdOS must **not** copy.
* **Every breaking-change surface is named and approved before it lands.** The new REST routes, the new migrations, the new column and the new table in this band are enumerated in `## Risks and blockers` R1–R9 and routed to `../Open Decisions.md`. A new socket event, a new shared type, a new migration, a new route and a new dependency are approved in the same wave that consumes them (`../Build Sequence.md`).
* **Docs move with the code.** The owning Domain Spec is updated in the **same task** as every code change in this band (`AGENTS.md` §6), and the `UX_GUIDELINE.md:76` `[pending]` marker is removed in the same task as the run-branch graduation, not before.
* **Planned and pending product features are not built.** The "add agent to channel" verb (RE-P4-06 option B), the permission-blob enforcement (RE-P4-05) and the Electron fuse configuration and crash reporting (RE-P4-11) all require sign-off and are routed to `../Open Decisions.md` rather than built on inference (`AGENTS.md` §5.13).
