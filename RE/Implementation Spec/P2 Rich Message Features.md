# P2 Rich Message Features

> Type: Spec — Status: draft — Updated: 2026-10-21

## Purpose

CrowdOS's chat area is deliberately calm: six message types, folded tool calls, a chip-based mention router, a hover-reveal action toolbar and one honest status line. Discord's chat is dense with secondary features — reaction bubbles, a per-message action vocabulary, link previews, per-message threads, channel pins, fuzzy mention matching, slash commands, and copy/forward affordances.

This spec takes the P2 band of that vocabulary and turns each item into an **executable, additive** change to CrowdOS. It does not restyle the chat, does not replace CrowdOS's routing model, and does not re-implement anything the Threads, Messages or Channels domains already own.

Two rules govern every item below:

1. **CrowdOS is canon.** Where a Discord mechanism conflicts with a locked CrowdOS rule, the CrowdOS rule wins and the conflict is recorded in `## Risks and blockers` — never silently applied.
2. **Nothing existing is removed.** Every item states, in its `Target (additive)` row, exactly what is preserved.

Scope of this document: the chat area's rich-message feature set (P2). Performance measurement, keyboard completeness, landmarks, motion arbitration and the status strip's real sources are P3 and live in `P3 Performance and Accessibility.md`.

### Priority scheme

| Band | Meaning |
|---|---|
| **P0** | Correctness, or a blocker on a locked budget. Ships before anything else. |
| **P1** | High-fidelity interaction parity with the existing CrowdOS contract — the interactions a user expects every day. |
| **P2** | Rich features. Valuable, additive, and safe to defer without breaking the product. |
| **P3** | Polish and rare paths. |

Every item in this document is **P2**. P0 and P1 items in the sibling specs are *dependencies*, not competitors: where an item here needs a P0/P1 foundation (for example the last-read anchor that RE-P0-02 owns), the dependency is named in the `Depends on` row and in `## Dependencies and build order`. An item whose P0/P1 dependency has not landed is **blocked, not improvised** — it waits.

### Item IDs

The `RE-P2-nn` ids in this document are **authoritative for the P2 band**: `RE-P2-01`…`RE-P2-09`, and nothing else. `RE/Implementation Spec/Traceability Matrix.md` has been **reconciled** against the five parallel documents: it now cites the real ids, its reverse index covers all **41** of them, and no reserved or placeholder id remains — see `## Risks and blockers` #15. Nothing in the matrix is edited here.

### Additive rule

Every item is additive. Additive means:

- **No existing CrowdOS feature, slot, view, store slice, socket event or behaviour is removed, renamed or re-skinned.**
- Where an item adds a surface, it adds a *new* surface in the *existing* slot map. A new right-hand surface is a new `rightPanelView` enum value, never a boolean and never a second addressing scheme (`UX_GUIDELINE.md:32`).
- Where Discord's mechanism is incompatible with a CrowdOS rule, the item **re-shapes** it and says so in `Target (additive)`, and the conflict is listed in `## Risks and blockers`.
- Every `Target (additive)` row names what survives unchanged. A reviewer who cannot name what is preserved has not read the item.

### Acceptance criteria

Acceptance criteria are **objectively testable**. Each statement is either true or false when the item lands, checked by the named test or by a manual assertion in the item's `Steps`. "Looks good", "feels right" and "consistent with Discord" are not acceptance criteria and must not appear.

### Definition of Done (per item)

Every item's Definition of Done is AGENTS.md §2, verbatim in force:

1. **Repo scripts only.** Never call the underlying tools directly — use `npm run typecheck`, `npm run lint`, `npm test`, `npm run lint:gates` from the repo root (and the workspace-scoped variants). `npm run check:docs` does **not** exist yet; if a task needs it, the item is blocked on building it.
2. **Test through the public surface.** Client behaviour is tested through the store or a pure model module; server behaviour through the domain gate (`messageGate`, `threadGate`, …). Do not reach into another domain's internals. The client test environment is `node` (`packages/client/vitest.config.ts:6`) with no DOM and no Testing Library, so client acceptance is asserted against **pure model modules** and store actions, not rendered markup. Adding a DOM test environment is a new dependency and is routed to `## Risks and blockers`.
3. **Code change ⇒ docs update in the same task.** Touching a gate shape updates that domain's `Domain Spec`; touching a flow updates the `Feature and Flow Spec`; a gate-shape change also updates the root `_index.md` if gates move.
4. **§9 report.** The final report uses the exact AGENTS.md §9 shape: `Cause` · `Changed` · `Tests added` · `Checks` · `Blast radius` · `Invariants` · `Docs updated` · `Not done`, then the `commit?` question.

## Scope

**In scope**

- The channel transcript's per-message affordances: reactions, the action toolbar, mark-unread, link previews, message-anchored threads, channel pins/bookmarks.
- The composer's mention matching and the addition of a command surface.
- The clipboard-borne actions: copy id, copy link, forward.

**Out of scope**

- Anything in `P3 Performance and Accessibility.md` (measurement harness, keyboard completeness, landmarks and live regions, motion arbitration, status-strip sources, stream reconciliation, contrast verification).

## User Decision:

## Target Contract

> Status: Target. CrowdOS's chat area stays calm, honest and canon. The P2 rich-message band is **additive only**: every item below adds a capability without removing, renaming or re-skining an existing CrowdOS surface, and every item states what is preserved.

* **Nothing existing is removed, renamed or re-skinned.** The six message types, the folded tool calls, the 300 s grouping rule, the chip-based mention router, the hover/focus toolbars, the one status line, the composer caps and the follow/pin scroll contract all survive every item in this document unchanged.
* **The mention-chip channel is the routing source of truth and stays that way.** Reactions are display-only and never appear in `mentions[]`. A forward carries no mention set. The chips remain the only input to routing (`UX_GUIDELINE.md:17`).
* **A new right-hand surface is a new `rightPanelView` enum value**, never a boolean and never a second addressing scheme (`UX_GUIDELINE.md:32`). Pins arrive as the sixth member; the other five keep their meaning.
* **Server-owned data lives in the domain that owns it.** Reactions, pins and read state are written only through the Messages and Channels gates. The client keeps projections in **separate small stores**, not in the 4234-line god store.
* **Every new wire shape is a breaking-change surface.** A new socket event name, a new shared type and a new DB migration are named, allocated and routed for sign-off before implementation — never assumed.
* **Permission refusals are reasons on a disabled control, not absent actions.** CrowdOS's model wins over Discord's structural `null`; the divergence is recorded, not silently applied.
* **The deep-link contract is not widened without approval.** "Copy link" copies a link CrowdOS can actually resolve; a message-scoped link is deferred.
* **The raw-mention wire format (`<@id>`) is rejected.** The chip model stays, and the draft-vs-sent divergence is promoted to a written, tested contract.
* **The run-thread model is not replaced.** A message-anchored thread is a child of a message inside the existing Threads domain; the run branch and the pending ThreadDrawer graduation are untouched.
* **Pins and bookmarks are distinct states.** Neither reuses the sticky-mention state nor the favourites overlay, and the favourites overlay still never mutates the shared channel tree.
* **Every new surface degrades honestly.** A failed embed fetch renders a plain-text link; an unknown segment hides; an empty panel shows an honest empty, never a mock.
* **The thread's message list stays non-virtualized for now, with the budget conflict recorded.** `UX_GUIDELINE.md:167` locks "virtualize past 500 channels / 2,000 messages" and the client has no windowing dependency; that conflict is recorded in `## Risks and blockers` and is **not** amended by this document.
* **Keyboard completeness and the existing ARIA contracts are not regressions.** Every new affordance is reachable without a pointer, and no surface loses its listbox, tree or tab semantics (`UX_GUIDELINE.md:150-151`).
* **A code change updates its docs in the same task**, and every item closes with the AGENTS.md §2 definition of done and the AGENTS.md §9 report.
