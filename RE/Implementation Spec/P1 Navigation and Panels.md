# P1 Navigation and Panels

> Type: Spec — Status: draft — Updated: 2026-10-21

## Purpose

Bring the shell's navigation and its secondary surfaces up to the parity the CrowdOS guideline already promises, without touching the slot map, the named-view enum, or the existing affordances.

Six gaps:

1. `UX_GUIDELINE.md:59` describes a 56 px workspace rail that does not exist in code, and the guideline's own rule says it must be implemented **or** the guideline amended in the same task (RE-P1-01).
2. The roster lists every workspace agent regardless of channel, even though a per-channel participant set is already derived (RE-P1-02).
3. The right operations column is a hard-coded 260 px, so the 320 px end of the locked 260–320 px range is unreachable (RE-P1-03).
4. The `browser` view is unreachable below `xl`, which breaks "addressable from every width" (RE-P1-04).
5. `ThreadDrawer` is the one overlay without a focus trap, and it is mounted outside any `ErrorBoundary` (RE-P1-05).
6. The right-panel view is global rather than per-workspace, and `#view=` is parsed but never honoured on history navigation (RE-P1-06).

## How to read this spec

**Item shape.** Every item is a table with nine rows: `Area`, `CrowdOS current`, `Discord reference`, `Target (additive)`, `Steps`, `Acceptance criteria`, `Test`, `Priority`, `Depends on`, `Invariants`. `CrowdOS current` cites real `file:line` in this repo; `Discord reference` cites a `RE/Discord Findings/<Doc>.md` file and the specific mechanism it describes, or says plainly that Discord offers no reference.

**Priority scheme.**

- **P0** = correctness, or a locked-budget blocker. These are items where the code contradicts a locked CrowdOS rule or a `UX_GUIDELINE.md` §12 budget.
- **P1** = high-fidelity interaction parity.
- **P2** = rich features.
- **P3** = polish and rare paths.

This document is P1 only. P0 chat items live in `P0 Chat Core.md`.

**Every item is ADDITIVE.** No item removes, renames, re-skins, or reorders a CrowdOS surface, slot, view, enum member, or behaviour. Each `Target (additive)` row names explicitly what is preserved. Where a Discord pattern conflicts with a locked CrowdOS rule, the item is re-shaped to fit CrowdOS, and the conflict is recorded in `## Risks and blockers` — never silently applied. The two most important re-shapings here: the workspace rail goes **inside** the existing nav column rather than becoming a fourth column, and the channel-scoped roster is a **grouping inside** the existing `roster` view rather than a new `rightPanelView` member.

**Acceptance criteria are objectively testable.** Each one can be checked by running a command and reading a number, a DOM query, or a boolean.

**Testing surface constraint (read this before writing a test).** The client vitest environment is `node` (`packages/client/vitest.config.ts:6`) and the client has no `jsdom` and no `@testing-library/react` (`packages/client/package.json:15-26`). Component *rendering* is therefore not unit-testable today. Every item below separates a **pure logic module** (tested in the `node` vitest environment) from the component wiring, and adds a Playwright spec under `e2e/` where a real DOM assertion is the only honest way to check the behaviour. Adding a DOM test environment is **not** approved — it is in `## Risks and blockers`.

**Definition of Done** for an item = the repo's `AGENTS.md` §2:

- run the repo's own scripts only (`npm run typecheck`, `npm run lint`, `npm test`; `npm run test:e2e` for the Playwright specs) — never raw `tsc` / `vitest` / `eslint`;
- a test that goes through the public surface (the component's public props/store contract for the client; the socket/REST surface for transport code) — never another domain's internals;
- a code change ⇒ a docs update **in the same task** (`AGENTS.md` §6): `re-docs/Frontend Docs/Domain Spec/Workspace Shell.md`, `re-docs/Frontend Docs/Domain Spec/Chat Area.md`, `re-docs/Frontend Docs/Domain Spec/Stores.md`, `re-docs/Frontend Docs/Feature and Flow Spec/*` as affected, and `UX_GUIDELINE.md` wherever the change makes a guideline line true or false;
- an `AGENTS.md` §9 report at the end of the task, then an explicit `commit?` question. No commit without an explicit yes.

## Scope

**In scope** — `packages/client/src/App.tsx`, `packages/client/src/config/deep-link.ts`, `packages/client/components/workspace/{WorkspaceSidebar,WorkspaceDropdown,RightSidebar,OperationsSheet,BottomDrawer,ThreadDrawer,ChannelButton}.tsx`, and the chat-facing slices of `packages/client/stores/crowdOsStore.ts`, plus the `e2e/` specs that assert the DOM behaviour.

**Out of scope** — the transcript, the composer, mentions and the runtime contract (those are `P0 Chat Core.md`); the backend, the DB schema, the socket protocol, the settings modal and the portal's internals. No item in this document changes a socket event, a REST route, a `@crowdspace/shared` type, a Drizzle table or migration, an env var, or a feature flag.

**What this document must not become.** It is not a place to add a sixth `rightPanelView` member, a channel-pins bar, per-message threads, a per-channel right panel, a mobile layout, or a Discord-style role model. The `rightPanelView` enum is the single addressing scheme (`UX_GUIDELINE.md:32`, `:67`) and it stays a five-value enum.

- **RE-P1-01 shrinks the channel nav.** The rail takes 56 px out of a nav column that is `clamp(240px,20vw,280px)` (`App.tsx:205`), leaving 184–224 px for the channel tree — between 16 px and 56 px narrower than today at the clamp ends. The guideline currently describes a rail as a **separate** 56 px column; this item deliberately places it inside the nav column instead, so the guideline's slot map is wrong as written and must be corrected.
- **RE-P1-01 needs the aggregate badge counts, which do not exist yet.** The rail needs per-workspace unread, mention and approval-waiting counts. A per-workspace aggregate is a new derivation over the same projections — cheap, but it must be written so that the **same** projections feed both, or the rail and the sidebar will disagree. The approval badge must remain a third distinct badge (`UX_GUIDELINE.md:109`); the Discord pattern of one red dot for both is exactly what CrowdOS rejects.
- **RE-P1-01 is the one item that touches the slot map.** The three-column row is unchanged, but the nav column's internal composition changes, and `UX_GUIDELINE.md:59` must be amended. It is also the item most likely to draw a "you changed the shell" objection; the mitigation is that the row still has three children, the nav keeps its width class, and the portal still gates boot.
- **RE-P1-03 changes the width of all five right-panel branches.** The branch markup is duplicated between the reduced-motion early return (`RightSidebar.tsx:232-274`) and the animated path (`:276-357`). Applying the width at the `<aside>` level (`App.tsx:243`) rather than per branch is what keeps the two paths in sync; if a reviewer prefers per-branch widths, both copies must be edited and the two must be kept identical, which is a maintenance trap.
- **RE-P1-04 changes `UX_GUIDELINE.md:68`.** The line reads "an **ops bottom sheet** (Jobs / Approvals / Repo)". Adding the browser tab makes that list wrong. The amendment is required in the same task (`AGENTS.md` §6). The alternative — declaring the browser view desktop-only with a reason — is **not** available as it stands, because the Panels Target Contract already says "`browser` is a fifth member and MUST remain addressable from every width"; declaring it desktop-only would need that rule changed too, which is a bigger decision than adding a tab. If the operator judges the live 1 fps frame stream too heavy inside a bottom sheet, the alternative to land is to keep the tab and mount the existing panel, not to invent a reduced browser mode.
- **RE-P1-05's focus trap constrains a non-modal surface.** A `role="dialog"` without `aria-modal` that traps `Tab` is a deliberate compromise: the drawer is visually a column beside the chat, not a modal, but the trap contract requires focus to be confined. The drawer is small (320 px) and its content is a run branch or a thread list, so the trap is cheap; a wider drawer carrying a long branch would need revisiting. Note that declaring `aria-modal="true"` would be wrong **and** would break the shell's Escape arbitration at `App.tsx:140-146`, which queries `[role="dialog"][aria-modal="true"]` before letting the nav consume Escape.
- **RE-P1-05's `ErrorBoundary` step is separable.** It is one wrapper element, but it is not strictly part of "focus management". A reviewer who wants the focus fix alone can drop step 4 — the `ThreadDrawer` is still outside every `ErrorBoundary` afterwards, which remains an open gap against `re-docs/.../Workspace Shell.md`'s per-panel isolation property.
- **RE-P1-06 changes the shape of a store slice.** `rightPanelView` goes from a scalar to a per-workspace map. The **action** keeps its name and its signature, so no call site changes, but every *reader* of the slice must go through the new selector. A missed direct read of `state.rightPanelView` would show the wrong workspace's view. A grep for `rightPanelView` across the client must be part of the task's blast-radius check (`AGENTS.md` §1.5). The slice is currently **in-memory only** — it is initialised at `crowdOsStore.ts:1918` and no `crowdos_*` key holds it — so the new `crowdos_right_panel_view` mirror is a **net-new** key: there is no legacy value to migrate and nothing to clean up. The real risk is the **readers**, not the on-disk shape.
- **The deep-link view set widening touches a public surface.** `deepLinkView` (`deep-link.ts:15`) is exported and is the vocabulary a `crowdos://` URL uses. Widening it to name `roster`, `repo` and `browser` in addition to the existing three is additive — no existing URL changes meaning — but it is a public vocabulary and belongs in the `re-docs/Desktop Docs/Feature and Flow Spec/Notifications and deep links.md` update in the same task. The `inbox` alias keeps its existing meaning (`jobs`), so no existing deep link breaks.
- **No DOM test environment in the client.** `packages/client/vitest.config.ts:6` sets `environment: 'node'` and the client declares no `jsdom` / `@testing-library/react` (`packages/client/package.json:15-26`). Every item therefore extracts a pure module for unit testing and uses Playwright (`e2e/`) for DOM assertions. A DOM unit-test environment would let most of the acceptance criteria be checked in `npm test` instead of `npm run test:e2e` — **it is a new dependency and is not approved**; it needs a decision. Until then, the Playwright specs skip themselves when the dev stack is down (the pattern in `e2e/chat.spec.ts:10-14`).
- **The concurrent `e3fe5f5` commit may shift line numbers.** The file:line references in this document were taken against `main` at `e3fe5f5`. Any later commit that edits `App.tsx`, `RightSidebar.tsx`, `OperationsSheet.tsx`, `ThreadDrawer.tsx`, `WorkspaceSidebar.tsx`, `deep-link.ts` or `crowdOsStore.ts` invalidates them. Re-verify every `file:line` at the start of the task.

RE-P1-04 fixes the label; the `:32` count should be corrected in the same task. ## User Decision:

## Target Contract

> Status: Target. A correct implementation of this document satisfies every invariant below. CrowdOS's locked shell contract (`UX_GUIDELINE.md:32`, `:56-68`, `:177`) is **locked strength — extend, never churn**; the Discord corpus is a comparison, not a replacement.

* **The shell keeps one composition root and one named-slot map.** Slots never reorder or swap meaning, and the three-column row still has exactly three children: nav / centre chat / right ops (`App.tsx:190-249`).
* **A panel is addressed by the named view enum and nothing else.** `rightPanelView` stays a five-value enum (`roster | repo | jobs | telemetry | browser`), every writer goes through `setRightPanelView`, and the header tab strip keeps its `aria-selected` / `aria-controls` binding to it (`UX_GUIDELINE.md:32`, `:67`). No second addressing scheme is introduced by any item in this document.
* **The portal remains the boot surface.** The shell never renders before a workspace is entered (`App.tsx:165-175`, `UX_GUIDELINE.md:14`); the workspace rail is an in-shell switcher that adds to the existing nav column and never replaces the nav column, the dropdown or the portal.
* **Categories stay groups, never folders, and the shared channel tree is never mutated by a personal or workspace-level overlay** (`UX_GUIDELINE.md:15`, `:65`).
* **Every badge is icon + text, never colour-only, and the approval-waiting badge stays a third distinct badge** alongside unread and mention (`UX_GUIDELINE.md:51`, `:109`). Discord's single red dot is not a pattern CrowdOS copies.
* **Every state a user perceives without colour is carried in the control's accessible name**, not only in a class or a colour — the rule Discord's rail demonstrates and CrowdOS adopts.
* **Authority comes from the tier and never from a name, a species label, a role or a presence dot** (`AGENTS.md` §5.3, `UX_GUIDELINE.md:21`). The channel-scoped roster group is a membership view; the tier chip remains the only authority signal.
* **The roster is a derived view over the agents the workspace already has, never a second stored roster**, and it keeps its L0–L3 tier groups, the service-agent exclusion, the durational presence and the per-row Stop.
* **Every overlay that takes focus traps it and restores it.** `ThreadDrawer` joins the six overlays that already use `useOverlayFocus`; no overlay may be left behind with focus still inside it.
* **The right operations column is 260 px by default and resizable within the locked 260–320 px range**, with a keyboard-operable `role="slider"`, and the width is a per-workspace view preference — never a permission, never a shared setting.
* **Every `rightPanelView` member is addressable at every width.** Below `xl` the ops bottom sheet grows a tab rather than hiding a view, and ops are never fully hidden at any viewport (`UX_GUIDELINE.md:68`).
* **Navigation state is resolvable from the URL, and a deep link can never address something that does not exist.** The written hash shape stays `#<workspaceId>/<channelId>`; a malformed or unknown target is ignored and can never break the shell (`deep-link.ts:207-209`).
* **Every view preference is workspace-scoped.** The right-panel view map, the panel width and the rail's badge counts are all keyed by workspace and never leak between workspaces (`AGENTS.md` §5.10).
* **Every item in this document is additive.** The workspace dropdown and its four menu items, the channel tree and its categories, the favourites and recents overlay, the five right-panel views, the roster tiers, the ops sheet's three original tabs, the bottom drawer, the run-thread drawer's run and thread modes, and the portal all stay exactly as they are.
