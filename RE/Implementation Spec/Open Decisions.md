# Open Decisions

> Type: Map — Status: draft — Updated: 2026-10-21

## Purpose

This is the list of questions the Discord-derived programme cannot answer on its own. Each one is a choice with two or more defensible answers, where the choice changes what gets built and therefore has to be made by the person who owns the product — not inferred by an agent from a Discord finding.

Every decision below is **blocked for a stated reason**, and every one names the items it unblocks. Nothing here is a wish list and nothing here is a question the research corpus already answered: the corpus established *what Discord does*, and this document is about *what CrowdOS should do about it*.

Three of these decisions are **security- or scope-shaped** and cannot be deferred by choosing the conservative option:

- **#4** decides whether a stored permission blob is a boundary or a decoration. CrowdOS's own Agents Domain Spec says a stored-but-unenforced blob "is not acceptable as a security boundary" (`re-docs/Backend Docs/Domain Spec/Agents.md:147`), so the status quo is already a recorded defect — the decision is *which repair*.
- **#5** decides whether the agent profile picture is an uploaded image or a picked vector. The user asked for the first; the second is a different feature that happens to share the name.
- **#11** decides whether the specification documents are corrected before the code lands or alongside it. That choice governs every other wave in `../Build Sequence.md`.

**How to use this document.** Answer a row by replacing the **Recommendation** cell with the chosen option and a date. A row that has an answer becomes a one-line note in the item it blocked, and the item's `Depends on` field is updated in the same task. Rows are never deleted — a decided row stays, because "we chose this on this date" is the useful record.

## Not decided

These are **out of scope** for this programme, explicitly, so that they are not re-opened by a later agent reading the Discord corpus. None of them is a Pending product feature being smuggled in — each is either a deliberate absence or a different product's feature.

- **Voice and video** — voice channels, voice states, mute/deafen, push-to-talk, screenshare, the voice activity sub-text in the channel sidebar. CrowdOS is an agent workspace with no voice surface, and building one is a planned capability under `CrowdOS.md` §34 (`AGENTS.md` §5.13).
- **Native OS themes** — Discord's bootstrapper has zero `nativeTheme` occurrences; CrowdOS has its own in-app theme cycle with plain-language names (`packages/client/components/ui/ThemeToggle.tsx:33-38`). Nothing to adopt.
- **Emoji-only reactions as a routing mechanism** — never, under any option. CrowdOS's mention chips are the routing source of truth (`UX_GUIDELINE.md:17`), and a reaction that could route would invert that (conflict risk 9). Decision #3 is about *persistence and display*, not about routing.
- **A seventh message type** — the transcript keeps exactly six (`packages/client/types/crowdOs.ts:27`), and `UX_GUIDELINE.md:75` forbids adding one without a canonical spec row. Rich content, unfurls and reactions are **rendered inside** the existing types, not as new ones.
- **A second thread model** — CrowdOS's run thread is the Threads surface; Discord's reply-chain-per-message is a different product concept. The Canvas already states "Never add a second thread model" (`../CrowdOS Understanding/Canon and Locked Rules.md:29`).
- **A second right-panel addressing scheme** — every right-hand surface is a `rightPanelView` enum value (`packages/client/types/crowdOs.ts:323`). Discord's header popovers would be a second scheme and are refused (conflict risk 16). Decision #8 chooses between an enum value and a section, not between schemes.
- **A guild owner, an "administrator" bypass, or a 40-bit permission blob** — all three are forbidden by `AGENTS.md` §5.3 and all three are refused row by row in `../Traceability Matrix.md`. Decision #4 is about enforcing or removing CrowdOS's **own** blob, not about importing Discord's model.
- **A native quit-only application menu** — CrowdOS's tray template (`packages/desktop/main/tray-menu.ts:37-70`) is the single menu surface. Discord's quit-only menu is refused.
- **Slow mode as a silent block** — refused: CrowdOS confirms an over-cap send rather than blocking it (`UX_GUIDELINE.md:83`, `:201`). Any throttle must be an explicit, announced confirm (conflict risk 12).
- **Categories or guild folders as a real folder tree** — refused: `UX_GUIDELINE.md:15` ("never present Categories as folders"), conflict risk 13. Decision #9 is about the **rail**, not about folders.
- **A guild/folder-style server list with unread pills, mention badges and per-server ordering** — refused as a structure. CrowdOS's personal favourites overlay never mutates the shared channel tree (`UX_GUIDELINE.md:65`), and the nav slot is not replaced by a rail (conflict risk 1).

## User Decision:

## Target Contract

> Status: Target. These decisions are the product owner's to make. An agent may recommend, may quantify the blast radius, and may state what each option costs — it may not choose.

* **Every decision names its options, a recommendation, a blocking reason and the items it unblocks.** A decision without a blocking reason is not a decision; it is a note.
* **A recommendation is a recommendation, never an application.** No item's behaviour changes until the row is answered. RE-P4-05 in particular lands as a **decision record only** — the enforcement code is not written until decision #4 is answered.
* **A decision that changes a locked rule names the rule.** Decisions #1, #9, #10 and #13 each touch a locked slot map, a locked budget or a locked shell posture, and each says so.
* **A decision that changes a breaking-change surface names the surface.** Decisions #3, #5, #6 and #7 each add a migration, a schema, a socket event or a set of routes, and each says so.
* **The conservative option is not always the safe one.** Decision #4 is the clearest case: leaving the permission blob unenforced is not "no change", it is leaving a recorded defect open (`re-docs/Backend Docs/Domain Spec/Agents.md:147`).
* **Answering a row updates the items it blocked, in the same task.** The item's `Depends on` field, its `## Risks and blockers` entry and the matrix row all change together.
* **Answered rows are never deleted.** The row keeps its options and gains the decision and a date. "We chose this, on this date, for this reason" is the record that stops the question being re-litigated.
* **The out-of-scope list is a decision too.** The eleven entries in `## Not decided` are settled: they are not deferred, they are **refused** or out of scope, and they are listed so that a later agent does not re-open them from the same Discord document.
