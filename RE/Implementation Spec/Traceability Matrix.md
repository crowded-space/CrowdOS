# Traceability Matrix

> Type: Reference — Status: draft — Updated: 2026-10-21

## Purpose

This is the corpus-level map. It answers one question for every significant mechanism in the twelve Discord Findings documents plus the Evidence Index: **what did CrowdOS do with it, and where is that written down?**

The matrix is the anti-drift instrument for the whole Discord-derived programme. Without it, an adopted Discord mechanism has no owner, a rejected one has no recorded reason, and a reviewer cannot tell the difference between "we decided not to do this" and "nobody looked at this". Every row names the Discord mechanism, the CrowdOS surface that receives it, the spec item that implements it, and the verdict.

Three verdicts are used and they mean exactly what they say:

| Verdict | Meaning |
|---|---|
| **Adopted** | The Discord mechanism is taken as-is, or with only cosmetic reshaping, into the named CrowdOS surface. CrowdOS already had it, or CrowdOS is better off for having it. |
| **Adapted** | The mechanism is taken, but re-shaped to fit a locked CrowdOS rule. The row names the rule that forced the reshaping. |
| **Rejected** | The mechanism is deliberately **not** taken. The row names the locked CrowdOS rule that resists it. A rejection without a named rule is a defect. |

The rows are ordered by Discord document, and within a document by the significance of the mechanism. A document with many rejected rows is a document that describes a **different product** — that is the point of recording it.

## How it works

**The ID space.** Five spec documents contribute items: `RE-P0-nn` (Chat Core), `RE-P1-nn` (Navigation and Panels), `RE-P2-nn` (Rich Message Features), `RE-P3-nn` (Performance and Accessibility) and `RE-P4-nn` (Settings, Threads and Authority). The scheme and the counts are stated in `../_index.md`. All five documents now exist and their ids are **real**: this matrix cites the ids the documents actually use, and the reverse index below covers all **41** of them. Where a row's real home is outside this band, the `Spec item ID` cell names the owning band and the reader is pointed there.

**What kind of document this is.** This is a **reference artifact of the Spec kind**: it maps every Discord mechanism to the CrowdOS surface and the spec item that owns it, but it owns no item and states no new behaviour of its own. It therefore carries the reference H2 order, not the Spec H2 order — `../_index.md:41` requires "the same H2 order within its kind", and this is a reference kind. The P-documents carry the Spec kind and the Spec H2 order.

**The `Item band` column.** The fifth column of `## Structural inventory` is the band that **owns** the `Spec item ID` in that row — `P0`, `P1`, `P2`, `P3` or `P4`. It is the item's own band, never a priority: the row reads *the Discord mechanism → the CrowdOS surface → the spec item → the item's band → the verdict*. A row whose `Spec item ID` cell names items from two bands carries both bands, in the order the ids are listed; a row with no item id carries `—`.

**How a row was produced.** Each row was traced in this order:

1. **The Discord claim** — read in the Discord Findings document, with its own evidence pointer (`[Observed]` or `[Inferred]`, per `../Discord Findings/Evidence Index.md`).
2. **The CrowdOS surface** — read in the CrowdOS code at `file:line`, at HEAD `e3fe5f5`.
3. **The locked rule** — checked against `AGENTS.md` §5, `UX_GUIDELINE.md`, `CrowdOS.md` §25/§31/§34/§35 and `../CrowdOS Understanding/Canon and Locked Rules.md`.
4. **The verdict** — Adopted / Adapted / Rejected, with the deciding rule named.

**What this matrix does not do.** It does not restate the Discord findings (that would violate `../Discord Findings/Evidence Index.md`'s rule that a new finding must carry a new evidence pointer, not a paraphrase), and it does not restate CrowdOS's code. It points at both.

**How to read a rejected row.** A rejection is not a claim that Discord is wrong. Discord's guild model is a coherent product; CrowdOS is a different product with a different authority model. The rejection says: *this mechanism conflicts with a locked CrowdOS rule, and the CrowdOS rule wins.* Where a middle path exists, the verdict is **Adapted** and the row names it.

**The two Discord performance findings that change CrowdOS's plan.**

1. **Discord's message list is not virtualized** — 0 hits for `react-window`, `react-virtuoso`, `virtua`, `useVirtualizer`, `overscan` and `estimatedItemSize` across 1,606 loaded chunks; the chat renders one real DOM subtree per message, and the memory bound comes from store truncation (`truncateTop` / `truncateBottom`), not from windowing (`../Discord Findings/Message List.md:23-45`, `:134-141`). CrowdOS's locked budget says the opposite — "virtualize past 2,000 messages" — and it is **unmet**. So Discord's reference gives CrowdOS the **threshold pattern** and the **store-truncation primitive**, and nothing else. The gap is the reason RE-P0-06 is a P0 item and not a P2 item.
2. **Discord's virtualized list is used for the *member list*, not the chat** (`isVirtualizedList: rows.length >= 64`). CrowdOS's roster is the one list whose size grows with the workspace rather than with the history, so the threshold pattern lands there first.

**The performance cost this band adds.** RE-P4-01 introduces the product's first **binary** response path. Its cost is bounded by design: the blob is content-addressed, so the second reference to the same image costs **no** extra bytes, and the read is served from the local workspace folder with no database round-trip (`AGENTS.md` §5.12). The cost that must be measured rather than assumed is the **render** cost of an `<img>` in the roster row, which appears in up to 200 roster rows at once (`RightSidebar.tsx:178-182`). The measurement harness (RE-P3-01) must exist **before** RE-P4-01 lands, which is why Wave 1 precedes Wave 2 in `../Build Sequence.md`.

**The two costs this band removes.** RE-P4-09's server-derived branch removes the dependency of the run branch on the 200-message client mirror (`messagePagination.ts:15`), which today means a run's branch silently truncates on a busy channel. RE-P4-02's server-backed roles remove a full-roster replace on every agent mutation (`crowdOsStore.ts:3028`, `:3074` → `:1573`, `:2432`), replacing it with a single-role write.

## User Decision:

## Target Contract

> Status: Target. This matrix is the corpus's traceability record. It is not a design document and it never becomes one: a row says what was done with a Discord mechanism, not what should be built.

* **Every Discord mechanism has a row.** A mechanism with no row is an unexamined mechanism, and an unexamined mechanism is a defect in the corpus.
* **Every row names a CrowdOS surface, a spec item and a verdict.** A row without a spec item ID is either an already-built CrowdOS behaviour (and says so) or a gap (and appears in `## Gaps`).
* **Every rejection names the locked CrowdOS rule that resists it.** "Rejected" without a rule reference is not a verdict; it is an opinion.
* **The `Spec item ID` column only ever contains one of the 41 real item ids** from the five P-documents. There are no reserved references and no placeholders; the reverse index above covers every one of them.
* **Adoption is additive only.** A row marked Adopted never implies the removal or re-skin of a CrowdOS surface. CrowdOS keeps its slots, its enum, its six message types, its tier grouping, its modal settings and its own security policy.
* **Authority never comes from a role.** No row in this matrix authorises a role name, a role colour, a badge or a group header to grant, imply or gate a capability (`AGENTS.md` §5.3).
* **A budget row is never silently amended.** Where a Discord mechanism contradicts a §12 budget, the row says so and the budget is met or amended explicitly — never quietly (`UX_GUIDELINE.md:171`).
* **Gaps are stated, not implied.** Every Discord mechanism with no CrowdOS counterpart appears in `## Gaps` with the reason it has none. A deliberate absence is a decision, and it is recorded.
* **The matrix moves with the code.** A change to a Discord-derived surface updates the row that covers it, in the same task. A row that no longer describes the code is drift.
